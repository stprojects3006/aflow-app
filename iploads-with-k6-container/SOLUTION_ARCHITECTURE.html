🎯 Overview

This document provides a comprehensive view of the K6 Load Testing solution architecture, detailing how AWS Fargate, ECS, and other components work together to deliver scalable, serverless load testing capabilities.

Key Objectives

  • Serverless Load Testing: No server management required
  • IP Diversity: Multiple unique IP addresses for realistic testing
  • Scalable Architecture: Handle varying load testing requirements
  • Cost Optimization: Pay only for actual test execution
  • Comprehensive Monitoring: Real-time metrics and logging

🔧 Component Details

1. AWS Fargate (Serverless Compute)

Role: Provides serverless compute capacity for running k6 containers

Key Characteristics

  • No Server Management: AWS handles underlying infrastructure
  • Pay-per-Task: Only pay when containers are running
  • Automatic Scaling: Start/stop based on demand
  • VPC Integration: Direct network access with public IPs

Configuration

resource "aws_ecs_task_definition" "k6_task" { family = "${var.project_name}-k6-task" network_mode = "awsvpc" requires_compatibilities = ["FARGATE"] cpu = var.task_cpu memory = var.task_memory }

2. ECS (Elastic Container Service)

Role: Orchestrates container execution and management

Key Functions

  • Task Scheduling: Determines where to run containers
  • Resource Management: Allocates CPU/memory to tasks
  • Service Discovery: Enables container communication
  • Health Monitoring: Tracks container health

3. VPC Network Infrastructure

Components:

  • VPC: Isolated network environment
  • Public Subnet: Internet-accessible resources
  • Internet Gateway: Internet connectivity
  • Route Tables: Traffic routing rules
  • Security Groups: Network access control

Network Flow

ECS Task → Public Subnet → Internet Gateway → Internet → Target Application

4. S3 Storage

Role: Persistent storage for test results and logs

Storage Structure

5. CloudWatch Monitoring

Components:

  • Logs: Real-time container logs
  • Metrics: Performance and resource metrics
  • Dashboard: Visual monitoring interface
  • Alarms: Automated alerting

🔄 Request Flow Diagrams

1. IP Address Assignment Flow

Flowchart Steps:

  1. Deploy ECS Task → Fargate Allocates Resources
  2. VPC Assigns Private IP → Public Subnet Assigns Public IP
  3. Internet Gateway Routes Traffic → Security Group Validates Access
  4. Task Ready with Public IP → K6 Container Starts
  5. Load Test Script Executes → VUs Generate Requests
  6. Requests Use Container's Public IP → Target Application Receives Requests

Detailed Steps

# Task Deployment aws ecs run-task \ --cluster k6-cluster \ --task-definition k6-task \ --launch-type FARGATE \ --network-configuration "awsvpcConfiguration={subnets=[subnet-123],securityGroups=[sg-123],assignPublicIp=ENABLED}"

Fargate Resource Allocation

  • CPU: 1024 units (1 vCPU)
  • Memory: 2048 MiB
  • Network: awsvpc mode

IP Assignment Process

  • Private IP: Assigned from VPC subnet (10.0.1.0/24)
  • Public IP: Auto-assigned from AWS public IP pool
  • Network Interface: Each task gets dedicated ENI

2. Test Execution Flow

Execution Steps:

  1. Container Starts → K6 Script Loads
  2. Environment Variables Set → Target URL Configured
  3. Test Parameters Applied → VUs Initialize
  4. VUs Generate Requests → Network Stack
  5. Container Network Interface → Public IP: 3.x.x.x
  6. Internet Gateway → Internet → Target Application
  7. Response Received → K6 Processes Response
  8. Update Metrics → Log Results → Continue Test Loop

K6 Script Execution

// Load test script export default function () { const response = http.get('https://affluenceit.com/', { insecureSkipTLSVerify: true }); check(response, { 'status is 200': (r) => r.status === 200, 'response time < 2000ms': (r) => r.timings.duration < 2000, }); }

🔒 Security Architecture

Security Layers:

  1. ECS Task → IAM Roles (Task Role, Execution Role)
  2. Network Security → Security Groups, VPC Isolation
  3. Data Security → S3 Bucket Policy, CloudWatch Encryption
  4. Container Security → Non-root user, read-only filesystem

Security Components

# Task Role - Minimal permissions resource "aws_iam_role" "ecs_task_role" { # Permissions for S3 upload, CloudWatch logs } # Execution Role - Container startup permissions resource "aws_iam_role" "ecs_execution_role" { # Permissions for ECR pull, CloudWatch logs } # Security Group - Minimal required access resource "aws_security_group" "k6_sg" { egress { from_port = 0 to_port = 0 protocol = "-1" cidr_blocks = ["0.0.0.0/0"] } } # S3 Bucket Policy - Restrictive access resource "aws_s3_bucket_policy" "k6_results_policy" { # Only ECS task role can access }

📈 Scalability Considerations

Horizontal Scaling:

  1. Load Test Request → Multiple ECS Tasks
  2. Task 1: 10 VUs → IP 1: 3.1.1.1
  3. Task 2: 10 VUs → IP 2: 3.1.1.2
  4. Task 3: 10 VUs → IP 3: 3.1.1.3
  5. Task N: 10 VUs → IP N: 3.1.1.N
  6. All IPs → Target Application

Scaling Strategies

# Task-Level Scaling for i in {1..10}; do aws ecs run-task --cluster k6-cluster --task-definition k6-task done # Resource Scaling variable "task_cpu" { default = 2048 # 2 vCPU } variable "task_memory" { default = 4096 # 4GB RAM } # Geographic Scaling aws ecs run-task --cluster k6-cluster-us-east-1 aws ecs run-task --cluster k6-cluster-us-west-2 aws ecs run-task --cluster k6-cluster-eu-west-1

Cost Breakdown:

  1. Load Test Execution → Fargate Costs
  2. CPU: $0.04048/hour → Memory: $0.004445/hour
  3. Data Transfer: $0.09/GB → Storage: $0.023/GB/month
  4. Monitoring: $0.50/GB → Total Cost per Hour

Cost Optimization Strategies

# Resource Optimization variable "task_cpu" { default = 1024 # 1 vCPU - sufficient for most tests } variable "task_memory" { default = 2048 # 2GB RAM - optimal for k6 } # Execution Optimization aws ecs run-task --cluster k6-cluster --task-definition k6-task # Stop when complete - no idle costs # Storage Optimization resource "aws_cloudwatch_log_group" "k6_logs" { retention_in_days = 7 # Reduce storage costs }
